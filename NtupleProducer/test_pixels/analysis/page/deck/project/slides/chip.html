II · Route A: pixels in L1 · Readout chip

10 / 15 (+13 backup)

Route A assumed that the trigger could request pixel hits near its tracks within a few microseconds. The pixel readout chip does not allow that. Every group of pixels stores a time stamp with its hits, and the chip has one programmed latency: when a hit reaches that age, it is kept for readout if a trigger arrived for its crossing, and erased otherwise. Row A is normal running: the latency matches the L1 decision, so hits sit in the chip until 12.5 microseconds and nothing can read them earlier. Row B shows what setting the latency early would do: a request could be served, but every crossing without an early trigger would be erased before the normal L1 decision, so the rest of CMS would lose its pixel data. The RD53B design has a “two-level” mode built for an L0/L1 trigger option ATLAS once considered: a first trigger marks crossings and a later command selects them, but readout still happens after a second fixed delay, and it would need a first-level trigger for every crossing CMS might accept; neither experiment’s Phase-2 baseline uses two hardware trigger levels. Bandwidth would not be the obstacle for a future chip that allowed prioritised early reads (backup). The RD53C-CMS manual itself was not checked: to confirm with the chip experts.
